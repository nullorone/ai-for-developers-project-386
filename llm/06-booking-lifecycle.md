# Этап 6. Надежный жизненный цикл бронирования

## Промпт агенту

Ты — senior backend engineer, специализирующийся на транзакциях и concurrency. Реализуй создание, отмену гостем и перенос владельцем с сохранением инвариантов при гонках и повторных запросах.

Прочитай overview, требования, OpenAPI, модель данных и текущие тесты. Не подключай RabbitMQ: на этом этапе создаются только outbox records в той же транзакции.

## Цель

Гарантировать, что активный слот не может принадлежать двум встречам, а частичный сбой или повтор запроса не повреждает данные.

## Выполни

1. Реализуй `CreateBooking`:
   - нормализовать и валидировать input;
   - проверить, что слот будущий и входит в availability;
   - обработать `Idempotency-Key` с надежным хранением результата;
   - сгенерировать стойкий случайный management token;
   - сохранить только SHA-256-хеш;
   - транзакционно создать Booking, SlotReservation и `booking.created` OutboxEvent;
   - вернуть открытый token только в первом/идемпотентно восстановленном ответе согласно безопасно спроектированной схеме.
2. Если безопасное повторное возвращение token конфликтует с правилом хранения только хеша, выбери и документируй корректный контракт: например, повтор возвращает тот же booking без повторной выдачи секрета или idempotency record хранит зашифрованный краткоживущий response. Не сохраняй plaintext token бессрочно.
3. Реализуй получение cancellation details и `CancelBookingByGuest`:
   - token из заголовка;
   - constant-time сравнение хеша;
   - минимум персональных данных в ответе;
   - идемпотентная отмена;
   - транзакционно статус `CANCELLED`, удаление reservation и outbox `booking.cancelled`.
4. Реализуй `GetAvailableRescheduleSlots` и `RescheduleBookingByOwner`:
   - только будущая `CONFIRMED` встреча;
   - новый слот внутри availability;
   - атомарная замена reservation, изменение времени и outbox `booking.rescheduled`;
   - при конфликте вся транзакция откатывается и старый slot остается занят.
5. Переводи database unique violation в стабильный `409` code из OpenAPI.
6. Защити token endpoints rate limit и запрети логирование заголовка/секрета.
7. Добавь unit и integration/API tests счастливых путей, ошибок, повторов и rollback.
8. Добавь concurrency tests:
   - несколько созданий на один слот;
   - два переноса на один слот;
   - бронирование одновременно с переносом.
9. Обнови ADR по транзакционной модели и `docs/ai-development-log.md`.

## Ограничения

- Нельзя полагаться только на application-level pre-check.
- Нельзя удалять Booking при отмене.
- Нельзя освобождать старый слот до гарантированного успешного завершения переноса вне транзакции.
- Нельзя логировать guest comment, полный email, management token или Idempotency-Key.
- Не публикуй сообщения в RabbitMQ внутри database transaction.

## Критерии приемки

- В любой гонке на один слот существует не более одного SlotReservation.
- Повтор одинакового create request не создает второе бронирование/outbox event.
- Повтор отмены стабилен и не создает дубликаты событий.
- Неверный token не раскрывает наличие лишних персональных данных.
- После отмены слот снова доступен.
- После неуспешного переноса исходная встреча и reservation неизменны.
- Каждое успешное доменное изменение имеет ровно один соответствующий outbox event.

## Проверка

- Запусти все backend проверки и concurrency tests несколько раз.
- Проверь rollback с искусственно вызванной ошибкой между шагами use case.
- Проверь БД запросами на orphan Booking/SlotReservation и duplicate OutboxEvent.
- Выполни API smoke tests по OpenAPI.
- В финальном отчете объясни механизм concurrency и idempotency, а не только перечисли файлы.
