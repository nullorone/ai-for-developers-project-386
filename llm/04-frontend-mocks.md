# Этап 4. Frontend на mock API

## Промпт агенту

Ты — senior frontend engineer с продуктовым мышлением. Реализуй весь MVP-интерфейс поверх OpenAPI mock server, не обращаясь к внутренностям будущего backend.

Прочитай overview, требования, OpenAPI, `docs/api.md` и существующий frontend. Используй только сгенерированный API-клиент или тонкий адаптер над ним. Не меняй контракт ради удобства UI без явного анализа.

## Цель

Собрать проверяемые сценарии гостя и владельца до появления backend и доказать независимость разработки по контракту.

## Выполни

1. Реализуй маршруты с учетом GitHub Pages hash routing:
   - публичный календарь и бронирование;
   - подтверждение бронирования;
   - отмена по booking id и token из fragment route;
   - owner-доступность и список встреч;
   - owner-перенос встречи.
2. Реализуй выбор даты и 30-минутного слота без тяжелой календарной библиотеки, если она не нужна.
3. Реализуй форму гостя с валидацией имени, email и комментария.
4. Management token должен оставаться только в памяти/fragment URL; не отправляй его в analytics/logging и передавай API в `X-Booking-Token`.
5. Реализуй создание и удаление интервалов доступности.
6. Реализуй список будущих встреч и выбор нового свободного слота для переноса.
7. Для каждого запроса добавь loading, empty, validation, server error, conflict и success состояния.
8. При `409` обновляй список слотов и объясняй пользователю, что время уже занято.
9. Отображай время локально, но отправляй/получай UTC согласно контракту.
10. Обеспечь keyboard navigation, labels, focus management, читаемые ошибки и базовую адаптивность.
11. Добавь MSW или другой contract-aligned mock layer для компонентных/интеграционных тестов; источник примеров не должен расходиться с OpenAPI.
12. Добавь тесты ключевых UI-состояний и сценариев.
13. Обнови README frontend и `docs/ai-development-log.md`.

## Ограничения

- Не реализовывай backend и не читай будущую Prisma-модель.
- Не хранить management token в localStorage/sessionStorage.
- Не добавлять UI авторизации, recurring availability, отмену владельцем или перенос гостем.
- Не использовать реальные персональные данные в fixtures.
- Не оставлять критический сценарий только в виде статической верстки.

## Критерии приемки

- Все guest/owner happy paths можно пройти на mocks.
- Ошибки и пустые состояния доступны для воспроизведения.
- Отмена требует токен и корректно отображает повторную отмену.
- Неуспешный перенос сохраняет исходную встречу в UI.
- Время корректно показывается минимум в двух разных timezone-тестах.
- Build не зависит от запущенного mock server.

## Проверка

- Запусти lint, typecheck, unit/component tests и production build frontend.
- Выполни smoke flow с Prism/MSW.
- Проверь отсутствие management token в console output, test snapshots и persisted browser storage.
- В отчете перечисли маршруты, состояния и оставшиеся visual limitations.
