# Этап 2. OpenAPI-контракт

## Промпт агенту

Ты — API architect. Реализуй Design First контракт сервиса до написания frontend и backend.

Прочитай `llm/00-project-overview.md`, `docs/product-requirements.md`, ADR этапа 1 и текущее состояние репозитория. Если требования противоречат overview, остановись и явно сообщи о конфликте вместо молчаливого выбора.

## Цель

Создать валидный `openapi.yaml`, достаточный для независимой генерации mock API, frontend-клиента и backend-реализации.

## Выполни

1. Создай OpenAPI 3.1 контракт для всех endpoints из overview.
2. Опиши параметры получения слотов: UTC-границы диапазона, ограничения диапазона и формат ответа.
3. Опиши создание бронирования с заголовком `Idempotency-Key` и однократной выдачей management token/ссылочных данных.
4. Опиши просмотр и подтверждение отмены с `X-Booking-Token`.
5. Опиши owner endpoints доступности, списка встреч и переноса.
6. Создай переиспользуемые schemas для дат, pagination при необходимости, booking status, slot, ошибок и validation details.
7. Зафиксируй статусы минимум `200/201/204`, `400`, `401` или `403` для неверного management token, `404`, `409`, `422`, `429`, `500` там, где они применимы.
8. Добавь operationId, descriptions и реалистичные examples без персональных данных.
9. Добавь конфигурацию линтера OpenAPI, например Spectral, и npm-скрипт либо отдельную воспроизводимую команду проверки без создания общего workspace.
10. Добавь способ локального запуска mock server, например Prism, и опиши его в `docs/api.md`.
11. Обнови `docs/ai-development-log.md`.

## Важные решения

- Источник истины — корневой `openapi.yaml`, а не decorators будущего NestJS.
- Все timestamps — RFC 3339 UTC с суффиксом `Z`.
- Токен не должен встречаться в path/query параметрах backend API.
- Отмена повторяемая и возвращает стабильный результат.
- Перенос принимает новое начало слота; конец вычисляется системой.
- Формат ошибки един для всех операций и содержит стабильный машинный `code`.

## Критерии приемки

- OpenAPI документ синтаксически и семантически валиден.
- По нему можно получить mock для каждого happy path и ключевых ошибок.
- Все DTO закрыты от неожиданных свойств там, где это уместно.
- Контракт покрывает создание, отмену и перенос без неявных данных.
- Нет зависимости от внутренней Prisma-модели.
- Документация содержит команды lint и mock.

## Проверка

- Запусти OpenAPI lint.
- Запусти mock server или его smoke-проверку и обратись минимум к календарю, слотам и созданию бронирования.
- Проверь уникальность operationId.
- В финальном отчете перечисли endpoints, команды и любые осознанные отклонения от требований.
