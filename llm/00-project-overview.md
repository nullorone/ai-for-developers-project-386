# Проект «Запись на звонок»: описание реализации

Этот файл — единый источник контекста для всех этапов разработки. Перед выполнением любого этапа агент должен прочитать этот документ, соответствующий файл этапа и результаты уже завершенных этапов.

## 1. Цель проекта

Создать компактное законченное веб-приложение по мотивам Cal.com и пройти полный цикл разработки в подходе Design First. Владелец публикует доступные интервалы, гость выбирает свободный 30-минутный слот и бронирует звонок. Гость может отменить запись по защищенной ссылке, а владелец — перенести встречу на другой свободный слот.

Проект должен показать навыки, релевантные backend-вакансии: Node.js, NestJS, REST, PostgreSQL, RabbitMQ, транзакции, тестирование, Docker, CI/CD, эксплуатационная надежность и контролируемое применение LLM.

## 2. Технологический стек

- Frontend: React, TypeScript, Vite, TanStack Query, React Hook Form и schema validation.
- Backend: Node.js, NestJS, TypeScript, Prisma.
- API: REST, OpenAPI 3.1 как источник истины.
- Хранилище: PostgreSQL.
- Messaging: RabbitMQ, transactional outbox, retry и DLQ.
- Тесты: Jest или Vitest, Supertest, Testcontainers, Playwright.
- Инфраструктура: Docker, Docker Compose, GitHub Actions.
- Деплой: GitHub Pages для frontend; доступная бесплатная платформа для backend; managed PostgreSQL и RabbitMQ с подходящими бесплатными тарифами.
- Не используются: Kubernetes, gRPC, авторизация, внешние календари и настоящая отправка email.

## 4. Пользователи и сценарии

### Гость

1. Открывает публичный календарь по slug.
2. Видит свободные слоты в часовом поясе браузера.
3. Выбирает слот, вводит имя, email и необязательный комментарий.
4. Получает подтверждение и защищенную ссылку управления бронированием.
5. По ссылке просматривает краткие сведения и отменяет встречу.
6. После отмены слот снова доступен для бронирования.

### Владелец

1. Создает и удаляет интервалы доступности.
2. Видит список будущих подтвержденных встреч.
3. Выбирает встречу и доступный новый слот.
4. Переносит встречу; старый слот освобождается, новый занимается атомарно.

Авторизации и личных кабинетов нет. Owner-интерфейс публичен в рамках учебного ограничения; это явно указывается в README как неприемлемое ограничение для production.

## 5. Бизнес-правила

- В системе один seed-календарь и один владелец.
- Слоты имеют фиксированную длительность 30 минут.
- Границы доступности кратны 30 минутам.
- Пересекающиеся интервалы доступности запрещены.
- Прошедшие слоты не возвращаются.
- Время хранится и передается в UTC; frontend отображает локальное время пользователя.
- Бронировать можно только слот внутри опубликованной доступности.
- Одновременно активным для одного календаря и времени может быть только одно бронирование.
- Создание бронирования поддерживает `Idempotency-Key`.
- Отмена идемпотентна: повторный запрос сохраняет состояние `CANCELLED`.
- Перенос разрешен только для будущего подтвержденного бронирования и только в доступный свободный слот.
- Ошибка переноса не должна освобождать старый слот или частично менять бронирование.
- Отмененные бронирования сохраняются в истории, но в MVP owner-список показывает будущие подтвержденные встречи.

## 6. Защищенная отмена без авторизации

При бронировании backend генерирует криптографически стойкий management token. Открытый токен возвращается только в ответе на создание бронирования, а в PostgreSQL хранится SHA-256-хеш.

Frontend помещает токен во fragment URL после `#`, извлекает его в браузере и передает в заголовке `X-Booking-Token`. Токен нельзя писать в application/access logs или telemetry. Для публичных endpoints применяется rate limiting.

## 7. Основная модель данных

- `Calendar`: id, slug, title, description, owner timezone, timestamps.
- `AvailabilityWindow`: calendar id, startsAt, endsAt, timestamps.
- `Booking`: calendar id, startsAt, endsAt, guest data, status `CONFIRMED | CANCELLED`, managementTokenHash, cancelledAt, rescheduledAt, timestamps.
- `SlotReservation`: calendar id, booking id, startsAt, endsAt. Уникальность `(calendarId, startsAt)` защищает активный слот от гонок.
- `OutboxEvent`: event id, aggregate data, type, payload, status, attempts, timestamps.
- `NotificationLog`: event id, notification type/status, timestamps; уникальность по event id обеспечивает идемпотентность consumer.

При отмене `SlotReservation` удаляется. При переносе reservation заменяется в одной транзакции вместе с изменением `Booking` и созданием outbox event.

## 8. API верхнего уровня

Публичные endpoints:

- `GET /calendars/{slug}`;
- `GET /calendars/{slug}/slots`;
- `POST /calendars/{slug}/bookings`;
- `GET /bookings/{id}/cancellation`;
- `POST /bookings/{id}/cancellation`.

Owner endpoints:

- `GET /owner/availability`;
- `POST /owner/availability`;
- `DELETE /owner/availability/{id}`;
- `GET /owner/bookings`;
- `GET /owner/bookings/{id}/available-slots`;
- `PATCH /owner/bookings/{id}/schedule`.

Служебный endpoint: `GET /health`, при необходимости разделенный на live/ready.

Точные DTO, статусы и ошибки определяются в `openapi.yaml` на этапе 2. Ошибки имеют единый машиночитаемый формат. Конфликт занятого слота возвращает `409 Conflict`.

## 9. События RabbitMQ

- `booking.created`;
- `booking.cancelled`;
- `booking.rescheduled`.

Outbox event создается в одной PostgreSQL-транзакции с доменным изменением. Встроенный в NestJS publisher доставляет событие в RabbitMQ. Consumer того же backend-приложения имитирует уведомление и создает `NotificationLog`. Обработка идемпотентна, временные ошибки повторяются, исчерпавшие retries сообщения попадают в DLQ.

## 10. Нефункциональные требования

- Защита от конкурентного двойного бронирования на уровне PostgreSQL.
- Валидация всех входных данных и разумные ограничения диапазонов дат.
- Structured JSON logs и correlation/request id.
- Маскирование email, комментариев и секретных токенов.
- Graceful shutdown и health checks.
- Отказ RabbitMQ не блокирует успешную запись в БД.
- Адаптивный и доступный frontend с состояниями loading/empty/error/success.
- Независимые production-сборки frontend и backend.
- Воспроизводимый локальный запуск через Docker Compose.

## 11. Стратегия тестирования

- Unit: генерация слотов, пересечения, UTC и валидация.
- Integration: Prisma/PostgreSQL, транзакции, outbox и RabbitMQ через Testcontainers.
- API: счастливые пути, ошибки, идемпотентность и contract conformance.
- Concurrency: несколько бронирований или переносов на один слот.
- E2E: бронирование и отмена гостем; публикация доступности и перенос владельцем.

## 12. Деплой и ограничения бесплатного окружения

Цель: frontend на GitHub Pages, backend на Render/Koyeb или актуальном аналоге, PostgreSQL на Neon/Supabase или аналоге, RabbitMQ у managed-провайдера с бесплатным тарифом. На этапе деплоя нужно сверить актуальные условия по официальной документации и не применять искусственные keep-alive обходы.

Холодный старт, сон backend, лимиты сервисов и невозможность постоянной работы consumer должны быть честно описаны. Если бесплатный хостинг не позволяет постоянно держать consumer, локальный Docker Compose остается эталонным полным окружением, а облачное ограничение фиксируется в README.

## 13. Правила работы агента

- Выполнять только текущий этап и не реализовывать последующие заранее.
- Перед изменениями изучать текущее состояние репозитория и сохранять совместимость с уже принятыми решениями.
- Не менять `openapi.yaml` молча: изменение контракта требует явного обоснования и синхронизации реализации.
- Не скрывать упавшие проверки и не ослаблять тесты ради зеленого CI.
- Не добавлять Kubernetes, gRPC, авторизацию, recurring availability, отмену владельцем, перенос гостем и настоящую почту.
- Не коммитить секреты, токены или реальные персональные данные.
- Предпочитать простое решение, достаточное для MVP; значимые решения фиксировать в ADR.
- В конце каждого этапа обновлять `docs/ai-development-log.md` краткой записью: задача, использованный подход, проверки, обнаруженные риски.
- Финальный отчет этапа должен перечислять измененные файлы, выполненные проверки, результаты, ограничения и следующий ожидаемый этап.
