# ADR 0003. Транзакционная модель жизненного цикла бронирования

Статус: принято (этап 6, 2026-08-27).

## Контекст

Создание и перенос могут одновременно претендовать на один слот. Application-level
`find-before-insert` не защищает от гонки. Создание также должно безопасно воспроизводить
первый ответ по `Idempotency-Key`, хотя management token в открытом виде в `Booking`
хранить запрещено.

## Решение

Все изменения Booking, активной SlotReservation и OutboxEvent выполняются одной
PostgreSQL-транзакцией. Partial unique index `reservation_one_active_slot` остается
окончательным арбитром: для `(calendar_id, starts_at)` допустима только одна `ACTIVE`
reservation. Ошибка unique constraint переводится в стабильный `409 SLOT_TAKEN`;
rollback восстанавливает старую reservation и время встречи.

Advisory transaction locks дают стабильные повторные операции и согласуют команды с
удалением availability. Они не заменяют unique index: инвариант сохраняется для любого
writer, в том числе не использующего application locks.

Отмена блокирует конкретный Booking, сверяет SHA-256 токена constant-time сравнением,
записывает `CANCELLED`, удаляет активную reservation и создает единственное событие.
Повтор видит терминальный статус и не создает новое событие. Перенос на текущее время —
no-op без `rescheduledAt` и события.

Для create-idempotency хранится scope `(calendar, CreateBooking, SHA-256(key))`, хеш
нормализованного запроса, TTL 24 часа и полный первый ответ, зашифрованный AES-256-GCM
отдельным ключом окружения. Это позволяет в пределах контрактного TTL вернуть тот же
management token, не сохраняя plaintext. После TTL запись не воспроизводится и удаляется
при следующем create с тем же ключом; просроченные записи также можно безопасно удалять
операционным cleanup по индексу `expires_at`. В `Booking` всегда остается только SHA-256.

Outbox на этом этапе только записывается. Публикации в RabbitMQ внутри транзакции нет.

## Последствия

- Сбой на любом шаге, включая outbox insert, откатывает все доменные изменения.
- Два create/reschedule или create одновременно с reschedule не могут оставить две
  активные reservation одного слота.
- Потеря `IDEMPOTENCY_ENCRYPTION_KEY` не влияет на Booking, но делает сохраненные ответы
  невоспроизводимыми; ротация требует учитывать максимальный TTL 24 часа.
- In-memory rate limiter достаточен только для одного HTTP-процесса MVP. При
  горизонтальном масштабировании нужен общий limiter/proxy; database-инварианты от этого
  ограничения не зависят.
