# ADR 0001. Scope MVP и базовая архитектура

- Статус: принято
- Дата: 2026-08-26
- Этап: 1 (требования и продуктовые правила)
- Контекст-источник: [`llm/00-project-overview.md`](../../llm/00-project-overview.md)
- Связанный документ: [Продуктовые требования](../product-requirements.md)

## Контекст

Нужно построить компактное законченное веб-приложение «Запись на звонок»: владелец публикует интервалы доступности, гость бронирует свободный 30-минутный слот, отменяет его по защищенной ссылке, владелец переносит встречу. Проект учебно-портфельный, разрабатывается поэтапно с участием LLM-агентов, разворачивается на бесплатных тарифах и должен демонстрировать backend-навыки: NestJS, PostgreSQL, транзакции, RabbitMQ, тестирование, Docker, CI/CD.

Ключевые ограничения контекста: минимум функций, отсутствие аутентификации, отсутствие настоящих уведомлений и внешних календарей, необходимость независимой разработки frontend и backend, бесплатное окружение с холодным стартом и лимитами.

До начала реализации нужно зафиксировать четыре решения, влияющие на всю дальнейшую работу.

## Решение

### 1. Раздельные независимые проекты frontend и backend

`frontend/` и `backend/` — два самостоятельных проекта со своими зависимостями, скриптами сборки, тестами, Dockerfile и пайплайнами. Общего monorepo-workspace и общего пакета типов между ними нет. Единственная точка связи — корневой `openapi.yaml`; типы клиента генерируются из контракта в `frontend/src/shared/api/generated/`.

Причины:

- разные среды выполнения и разные площадки деплоя (статический хостинг против сервера приложений);
- независимые сборки и релизы; сбой одного проекта не блокирует другой;
- контракт как единственная связь заставляет держать API честным и проверяемым;
- отсутствие общего workspace убирает связность инструментов и упрощает CI на бесплатных раннерах.

Цена: часть типов дублируется, а синхронизация контракта и кода требует дисциплины и проверок в CI.

### 2. Design First: `openapi.yaml` — источник истины

Контракт OpenAPI 3.1 пишется на этапе 2, до frontend и backend. Из него генерируются mock-сервер, клиент frontend и контрактные проверки backend. Контракт не выводится из декораторов NestJS и не меняется молча: любое изменение сопровождается обоснованием и синхронной правкой реализации, документации и генерируемого клиента.

Причины:

- frontend можно разрабатывать на mock-сервере параллельно с backend;
- поведение API обсуждается и фиксируется до того, как его закрепит реализация;
- контрактные тесты дают объективную проверку совместимости двух независимых проектов.

Цена: изменение API дороже, чем при code-first; требуется дисциплина обновления контракта первым.

### 3. Отсутствие аутентификации и авторизации

Аутентификации нет ни для гостя, ни для владельца. Owner-эндпоинты и owner-интерфейс публичны. Единственный секрет продукта — management token гостя: криптографически стойкий случайный секрет, из которого в базе хранится только SHA-256-хеш; он передается в заголовке `X-Booking-Token` и живет в fragment части ссылки.

Причины:

- аутентификация владельца явно исключена из scope и потребовала бы пользователей, сессий, восстановления доступа и отдельного UI;
- продуктовая ценность MVP демонстрируется без нее;
- защита конкретного бронирования токеном показывает работу с секретами без полноценной системы доступа.

Явно отвергнуто: «скрытая» защита owner-маршрутов секретным путем, статическим заголовком, паролем в переменной окружения или фильтром по IP. Такая защита создает ложное ощущение безопасности и маскирует настоящее ограничение.

Цена: owner-функции может выполнить любой посетитель. Ограничение фиксируется в README и продуктовых требованиях как неприемлемое для production; смягчается ограничением частоты запросов и сокращением персональных данных в owner-ответах.

### 4. Отсутствие выделенного worker-сервиса

Publisher outbox и consumer уведомлений работают внутри того же процесса NestJS, что и HTTP API. Отдельного развертываемого worker-приложения нет. Надежность обеспечивается transactional outbox: доменное изменение и событие пишутся в одной транзакции PostgreSQL, публикация в RabbitMQ выполняется после ее фиксации, обработка идемпотентна, исчерпавшие повторы сообщения уходят в DLQ.

Причины:

- бесплатные тарифы обычно позволяют держать один постоянно работающий сервис;
- один процесс проще запускать, наблюдать и тестировать, включая Testcontainers;
- outbox уже дает главное свойство надежности — отсутствие потери событий при недоступности брокера, независимо от того, где живет publisher.

Цена: фоновая обработка конкурирует за ресурсы с HTTP-запросами, а сон бесплатного хостинга может задерживать доставку. При необходимости выделение worker выполняется без изменения доменной модели, поскольку outbox от места публикации не зависит.

## Альтернативы

| Альтернатива | Почему отвергнута |
| --- | --- |
| Monorepo с общим пакетом типов | Скрывает контракт за общим кодом, усложняет независимые сборки, не демонстрирует Design First |
| Code First (генерация OpenAPI из NestJS) | Frontend не может стартовать параллельно; контракт становится следствием реализации |
| Fullstack-фреймворк с SSR вместо SPA + отдельного API | Не показывает целевые backend-навыки и мешает статическому хостингу frontend |
| Простая аутентификация владельца (basic auth, пароль в env) | Выходит за scope; в текущем виде дала бы иллюзию защиты без модели пользователей |
| Прямая публикация в RabbitMQ из обработчика запроса без outbox | Теряет события при сбое брокера, нарушает целостность «изменение — событие» |
| Отдельный worker-сервис | Избыточно для MVP и плохо укладывается в лимиты бесплатных тарифов |
| Периодический polling базы вместо брокера | Не демонстрирует работу с очередями, которая является целью проекта |

## Последствия

Положительные:

- frontend и backend разрабатываются и деплоятся независимо, совместимость проверяется контрактом;
- поведение продукта зафиксировано до реализации, что снижает переделки;
- отсутствие auth сокращает объем работы и оставляет фокус на транзакциях, конкурентности и надежности обмена событиями;
- один процесс упрощает локальный запуск и тестирование.

Отрицательные и принятые:

- owner-функции публичны — критичное для production ограничение, зафиксированное явно;
- изменение API требует правки контракта и обеих реализаций;
- фоновая обработка делит ресурсы с API и зависит от режима работы бесплатного хостинга.

Решение пересматривается, если в scope добавляются несколько владельцев или календарей, настоящие уведомления, либо если нагрузка потребует отдельного worker.
